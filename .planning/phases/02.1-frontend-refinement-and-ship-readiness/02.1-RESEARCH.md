## Revalidation Against UI Review

Some review findings are already partially addressed by completed Plan 02.1-03 (mobile drawer, header labels, sidebar interactions). Remaining high-value gaps still present in codebase:

- Console-only failure handling in dashboard load paths (user sees weak/no inline failure context).
- Missing confirmation guard for destructive account action.
- Hardcoded auth error color classes (`text-red-500`, `bg-red-500/10`) bypass tokenized system.
- Arbitrary spacing values in key dashboard surfaces (`max-w-[200px]`, `min-h-[120px]`, `min-h-[100px]`).
- Revamp-level design consistency work (token constraints + guardrails) is not encoded as automated checks yet.

## Standard Stack

- Framework/runtime: Next.js App Router + React 19 + TypeScript strict.
- Styling: Tailwind v4 + tokenized custom CSS utilities in `web/src/app/globals.css`.
- Icons/motion: lucide-react, framer-motion.
- Testing/verification: ESLint, Next build, Playwright smoke (from Phase 02.1 release-gate plan).
- Accessibility approach: native semantic HTML first, ARIA only where semantics are missing.

## Architecture Patterns

1. **Primitive-first interaction contracts**
   - Centralize icon-only actions and binary toggles into reusable UI primitives.
   - Keep accessible name + keyboard semantics in one place.

2. **Status communication as a shared UI concern**
   - Use shared status/alert component for success/error/info feedback.
   - Replace page-local ad hoc banners and console-only catches.

3. **Destructive flow safety pattern**
   - Any irreversible action should have explicit confirmation + consequence copy.
   - Financial/auth redirects should preserve contextual message at destination.

4. **Design token governance + lightweight enforcement**
   - Keep color/typography/spacing through tokenized classes.
   - Add a small script gate to fail obvious hardcoded utility regressions.

## Do Not Hand-Roll

- Do not create custom keyboard/focus behavior when native `button`, `input`, `label` can provide semantics.
- Do not replace native checkbox semantics with div-only toggle controls without proper role/state wiring.
- Do not invent a bespoke state-management layer for this phase; local component state + shared UI components is sufficient.
- Do not add heavy visual-regression infrastructure in this phase; keep enforcement script + lint/build + smoke checks.

## Common Pitfalls

- Overusing `aria-label` when visible label text exists (`aria-labelledby` is preferred in that case).
- Binary toggles that animate visually but do not expose keyboard and state semantics.
- Error handling paths that log failures but never update visible user state.
- Introducing token bypasses during quick fixes (`text-red-500`, `bg-white text-black`, arbitrary `[Npx]` classes).
- Running UAT before revamp tasks complete, which creates stale acceptance evidence.

## Code Examples

### 1) Icon-only action button pattern

```tsx
<button
  type="button"
  aria-label="Close dialog"
  className="btn-ghost p-2"
  onClick={onClose}
>
  <X className="w-5 h-5" />
</button>
```

### 2) Binary switch semantics (button-based)

```tsx
<button
  type="button"
  role="switch"
  aria-checked={enabled}
  aria-label="AI personalization"
  onClick={() => setEnabled((v) => !v)}
  className={enabled ? "bg-accent" : "bg-bg-elevated"}
/>
```

### 3) Visible status message pattern

```tsx
{status && (
  <StatusBanner
    type={status.type}
    title={status.title}
    message={status.message}
  />
)}
```
